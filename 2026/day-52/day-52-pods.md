# Day 51 — Kubernetes Manifests and Pods

## Overview

Today I learned how to create Kubernetes Pods using YAML manifests and explored the basic structure of a Kubernetes manifest.

I also practiced imperative and declarative approaches, YAML validation, Pod labels, container access, logs, and Pod cleanup.

---

## 1. Kubernetes Manifest Structure

A basic Kubernetes manifest contains four important top-level fields:

```yaml
apiVersion: v1
kind: Pod

metadata:
  name: my-pod

spec:
  containers:
    - name: my-container
      image: nginx:latest
```

### apiVersion

Defines which Kubernetes API version is used.

For a basic Pod:

```yaml
apiVersion: v1
```

### kind

Defines the type of Kubernetes resource.

For this task:

```yaml
kind: Pod
```

### metadata

Contains identifying information such as the resource name and labels.

Example:

```yaml
metadata:
  name: nginx-pod
  labels:
    app: nginx
```

### spec

Defines the desired state of the resource.

For a Pod, this includes information such as the containers and images to run.

## 2. Nginx Pod

I created a simple Nginx Pod using a YAML manifest.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
spec:
  containers:
    - name: nginx
      image: nginx:latest
      ports:
        - containerPort: 80
```

Created the Pod using:

```bash
kubectl apply -f nginx-pod.yaml
```

Verified it using:

```bash
kubectl get pods
kubectl get pods -o wide
```

I also inspected the Pod:

```bash
kubectl describe pod nginx-pod
```

and checked its logs:

```bash
kubectl logs nginx-pod
```

I accessed the container using:

```bash
kubectl exec -it nginx-pod -- /bin/bash
```

Inside the container I tested Nginx:

```bash
curl localhost:80
```

The Nginx welcome page was returned.

## 3. BusyBox Pod

I created a second Pod using BusyBox.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: busybox-pod
  labels:
    app: busybox
    environment: dev
spec:
  containers:
    - name: busybox
      image: busybox:latest
      command: ["sh", "-c", "echo Hello from BusyBox && sleep 3600"]
```

Applied it:

```bash
kubectl apply -f busybox-pod.yaml
```

Verified it:

```bash
kubectl get pods
kubectl logs busybox-pod
```

The log output was:

```text
Hello from BusyBox
```

The `sleep 3600` command keeps the container running. Without a long-running command, the BusyBox container would exit.

## 4. Imperative vs Declarative Kubernetes

### Declarative Approach

In the declarative approach, I define the desired state in a YAML file and apply it using:

```bash
kubectl apply -f nginx-pod.yaml
```

Kubernetes then works to make the actual state match the desired state.

### Imperative Approach

An imperative command directly tells Kubernetes what to create.

Example:

```bash
kubectl run redis-pod --image=redis:latest
```

I then inspected the resource generated by Kubernetes:

```bash
kubectl get pod redis-pod -o yaml
```

This showed additional metadata automatically added by Kubernetes.

## 5. Generating YAML with Dry Run

I used:

```bash
kubectl run test-pod --image=nginx --dry-run=client -o yaml
```

This generates a Pod manifest without actually creating the Pod.

This is useful for quickly creating a YAML template that can then be modified.

---

## 6. Validating Kubernetes Manifests

Client-side validation:

```bash
kubectl apply -f nginx-pod.yaml --dry-run=client
```

Server-side validation:

```bash
kubectl apply -f nginx-pod.yaml --dry-run=server
```

The server-side validation sends the request to the Kubernetes API Server for validation.

I also intentionally modified the manifest to understand the validation errors produced by Kubernetes.

## 7. Pod Labels

Labels are key-value pairs attached to Kubernetes resources.

Example:

```yaml
labels:
  app: nginx
```

I viewed Pod labels using:

```bash
kubectl get pods --show-labels
```

I filtered Pods using:

```bash
kubectl get pods -l app=nginx
```

and:

```bash
kubectl get pods -l environment=dev
```

I also practiced adding a label:

```bash
kubectl label pod nginx-pod environment=production
```

and removing it:

```bash
kubectl label pod nginx-pod environment-
```

Labels are especially important because Kubernetes Services and other resources use selectors to identify Pods.

---

## 8. Pod Cleanup

I deleted the Pods created during the exercise:

```bash
kubectl delete pod nginx-pod
kubectl delete pod busybox-pod
kubectl delete pod redis-pod
```

Then verified:

```bash
kubectl get pods
```

A standalone Pod is not automatically recreated after deletion because there is no controller managing it.

This is one of the reasons Kubernetes Deployments are preferred for managing application workloads.

---

## 9. Key Learnings

* A Pod is the smallest deployable unit in Kubernetes.
* Kubernetes resources can be defined using YAML manifests.
* A basic manifest contains `apiVersion`, `kind`, `metadata`, and `spec`.
* `kubectl apply -f` follows the declarative approach.
* `kubectl run` is an example of the imperative approach.
* `--dry-run=client -o yaml` is useful for generating manifests.
* `kubectl describe` provides detailed resource information and events.
* `kubectl logs` displays container logs.
* `kubectl exec` allows access to a running container.
* Labels are used to organize and select Kubernetes resources.
* Standalone Pods are not automatically recreated after deletion.
* Deployments provide controller-based management of Pods.
